# 🎯 우파루 오딧세이 크로스 기댓값 계산기

650만 건 이상의 우파루 크로스 데이터를 기반으로  
최적의 크로스 조합과 기대값을 계산하는 분석 시스템입니다.

조합 계산 과정에서 발생하는 Runtime 성능 비용을 줄이기 위해  
사전 계산 기반 구조와 batch 처리 방식을 적용했습니다.

---

## 📌 프로젝트 배경

게임 내 크로스 조합은 경우의 수가 많아  
Runtime 시점마다 직접 계산할 경우 성능 비용이 크게 증가하는 문제가 있었습니다.

특히 데이터 규모가 커질수록  
응답 속도 저하 및 메모리 사용량 증가 문제가 발생했고,  
이를 해결하기 위해 사전 계산 기반 구조를 설계했습니다.

- cross-rate 기반 확률 및 기대값 계산

## 📦 데이터 수집 구조

Playwright 기반 크롤러를 직접 구현하여  
우파루 크로스 데이터를 수집했습니다.

장시간 데이터 수집 과정에서 안정성을 확보하기 위해  
다음과 같은 구조를 적용했습니다.

- CSV 기반 resume 처리로 중단 후 재시작 가능하도록 구현
- SPA 구조 대응을 위한 history.back() 기반 탐색 적용
- strict mode 충돌 회피를 위한 DOM 직접 탐색 방식 적용
- 진행률 및 ETA 출력 기능 구현
- 수집 완료 데이터 중복 방지 처리

## 🏗️ 핵심 설계

### 1. 사전 계산 기반 구조

초기에는 요청 시마다 기대값을 직접 계산하는 구조를 고려했지만,  
데이터 규모가 증가할수록 Runtime 연산 비용이 급격히 증가하는 문제가 있었습니다.

이를 해결하기 위해  
기대값을 미리 계산하여 저장하는 사전 계산 구조를 적용했습니다.

이를 통해 조회 시 복잡한 연산 없이  
즉시 결과를 반환할 수 있도록 설계했으며,
Runtime 시점의 반복 계산 비용을 최소화했습니다.

---

### 2. Batch 기반 대용량 데이터 처리

650만 건 규모 데이터를 약 10분 내 적재할 수 있도록  
JdbcTemplate 기반 batch insert 방식을 적용했습니다.

대량 INSERT 과정에서 발생하는 성능 저하를 줄이기 위해  
chunk 단위 처리 구조를 적용하여 처리 효율을 개선했습니다.

## 🚨 트러블슈팅

### AWS Free Tier 환경에서 메모리 부족 문제 발생

#### 문제

AWS Free Tier 환경에서 PostgreSQL 및 애플리케이션을 함께 운영하는 과정에서  
메모리 부족 현상이 발생했습니다.

특히 1GB 메모리의 제한된 AWS Free Tier 환경에서  
주기적으로 실행되는 dnf 프로세스가 메모리를 점유하면서 시스템이 종료되는 현상이 발생했습니다.

---

#### 원인

- Free Tier 인스턴스의 제한적인 메모리 환경
- PostgreSQL + 애플리케이션 동시 운영
- 대용량 데이터 처리 시 순간 메모리 사용량 증가

---

#### 해결

- swap 메모리 설정을 통해 메모리 부족 문제 완화
- batch 단위 데이터 처리 적용
- 불필요한 메모리 사용 최소화
- Runtime 계산 제거를 통해 서버 부하 감소

---

#### 결과

- 1GB 메모리 환경에서도 안정적으로 서비스 운영
- 약 650만 건 데이터 처리 안정성 확보
- 대용량 처리 과정에서도 서버 다운 없이 운영
- 기대값 조회 성능 개선
